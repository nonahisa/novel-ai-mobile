## 2. 作りの骨組み

### 2.1 Capacitor と WebView

**【案】** アプリは Capacitor で作り、画面は Android の WebView（Android System WebView。Chromium）に出す。

- 拡張機能の画面（原稿エディターなど）も Chromium の上の HTML なので、組み方の知見と画面の部品を持っていける
- 共有するコード（2.2）は TypeScript のまま動く
- iOS へも同じ形で広げられる（投稿キットは既に「クリップボードと URL を開くだけ」で作ってあり、方式を変えずに移せる。設計書 6.68）

Android System WebView は端末ごとに版が違う。**動かす下限は Chromium 105**（CSS Custom Highlight API が使える版。5.7）とし、下回る端末では用語の色だけを出さない。

### 2.2 拡張機能と共有するコード

拡張機能の `src/models/`・`src/core/`・`src/ai/`・`src/prompts/` を共有する。共通設計書 1.3 の見立てでは約2.3万行がそのまま使える。**同じコードを使えば、共通設計書2章の決まりの多くは同じに守られる。**

**【決定】** 2026-10-31 作者「試作で決める」：共有は写しを作らず、拡張機能のリポジトリのソースをそのまま取り込む（npm のワークスペース、または固定した版のパッケージとして参照する）。写しを持つと、拡張機能で直した不具合が Android に届かない日が来るためである。**どちらの取り込み方にするかは最初の試作（10章の段0）で両方を試してから決める。**

**【決定】** 2026-11-04 作者の裁定：共有の部品は**いつも本体（拡張機能）と同じ版**で取り込み、本体の版が上がるたびに取り込み直してモバイル版を出し直す。`設定/` の台帳は同期で本体と共有するので、古い部品が台帳の新しい欄（例：0.123.0〜0.125.4 で投稿の台帳に増えた revisions・bodyHash など）を落として書き戻さないようにするためである。取り込みの段取りは `docs/引継ぎ書.md` 2章に書く。

**【決定】** 2026-11-05 段0の試作で両方を試した結果（作者「試作で決める」2026-10-31 による）：**本体のタグを指す依存（版を固定したパッケージ）で取り込む。** `package.json` に `"novel-ai-assistant": "github:nonahisa/novel-ai-assistant#vX.Y.Z"` と書き（試作は v0.126.2 で行い、同じ日に v0.127.0 へ上げた）、画面のコードは `src/shared.ts` を通して `novel-ai-assistant/src/models/...`・`.../src/core/...` を読む。

| | 本体のタグを指す依存（採った） | ワークスペース（本体をこのリポジトリの中に置く） |
|---|---|---|
| 取り込んだ版の記録 | `package.json` の `#vX.Y.Z` の1か所。lock が commit まで固定する | サブモジュールの commit。タグとの対応は別に書く必要がある |
| 入る物 | 本体と、本体の実行時の依存（`buffer`・`diff`・`fflate`・`iconv-lite`・`path-browserify`・`undici`）だけ。`node_modules` 195MB・175個 | 本体の開発用の依存まで入る（229MB・374個）。本体の部品の組み立ての許可も求められる |
| テスト | こちらのテストだけが走る | Vitest が本体のテスト 1,584 ファイルまで拾い、そのままでは終わらない（除外の設定が要る） |
| CI | `pnpm install` だけ | サブモジュールの取得が要る |
| 本体の版上げ | `pnpm add "novel-ai-assistant@github:nonahisa/novel-ai-assistant#vX.Y.Z"` の1行 | サブモジュールをタグへ動かし、`pnpm install` |
| 写しを作らない・こちらで直さない | `node_modules` の下にあるので、こちらで直しても次の取り込みで消える（直さない決まりと合う） | 手元で本体のファイルを直せてしまう |

どちらでも型の検査（`tsc`）・テスト・画面のビルドは通った。取り込みに要る手当ては次の3つで、どちらの方式でも同じ：

- 本体の `core/pathText.ts`・`core/paths.ts` は Node の `path` を読むので、`vite.config.ts` で `path-browserify` へ差し替える（本体のブラウザ版と同じ）
- 本体の `core/runtime.ts` が `process` を（有無を確かめてから）読むので、型の検査に `@types/node` を入れる。端末で Node のものを読んでいないかは `androidReach.test.ts`（2.4）が見張る
- 本体の `core/textEncodePreserving.ts` が `import iconv = require("iconv-lite")` と書くので、型の検査の `module` を `preserve` にし、`erasableSyntaxOnly` を外す（2026-11-05。画面のビルドはそのままで通る）
- 取り込んだ版を画面に出す（動作確認ページの「本体の部品」の行。`vite.config.ts` が本体の `package.json` から版だけを埋める）

弱みは、本体のリポジトリを丸ごと取ってくること（文書や画像を含め 93MB。取得に約35秒）。困るほどになったら、本体の側で配る物を絞る（`files`）ことを母艦へ相談する。

依存の向きは拡張機能と同じにする：`画面` → `機能` → `core` → `models`。Android の画面のコードは `core` を呼ぶだけで、`core` の側に Android の事情を入れない。

### 2.3 差し替える部品

端末の機能に触れる部品だけを、Android 用に差し替える。**差し替えた部品も共通設計書2章を守る。** 守れていることは、拡張機能の同じ部品が通しているテストを、Android の部品にも通して確かめる（9章）。

| 部品 | 拡張機能 | Android | 守る決まり |
|---|---|---|---|
| ファイルの場所（`core/paths.ts`） | `vscode.Uri` | Capacitor のファイルの場所（`Directory.Data` の下） | 作品フォルダーの形（共通設計書 3.1） |
| 本文の読み書き（`core/textFile.ts`） | `vscode.workspace.fs` | `@capacitor/filesystem` | ハッシュの照合・文字コードと改行の保持・変わった所だけ・退避（共通設計書 2.1）。`writeTextFilePreservingFormat` の中身は共有し、下の読み書きだけを差し替える |
| 端末の識別（`core/device.ts`） | VS Code の機械ID | アプリを入れたときに作る ID を端末の設定に置く | 端末ID は同期しない（共通設計書 3.4・3.6） |
| git（`core/git.ts`） | `git` コマンド | `isomorphic-git` | 共通設計書 2.8（6章） |
| AI への通信（`ai/httpClient.ts`） | `fetch` | `CapacitorHttp` | 鍵を URL に載せない（共通設計書 2.9） |
| 待ち時間（`ai/fetchTimeouts.ts`） | undici | 時計と中止の印で組み直す | 既定300秒（共通設計書 4.5） |
| 鍵の保管（`SecretStorage`） | VS Code の `SecretStorage` | Android Keystore で暗号化した保管 | 平文の設定ファイルに置かない（共通設計書 2.9） |
| 端末の設定（`globalState`） | VS Code の `globalState` | `@capacitor/preferences` | 作品フォルダーに置かない |

### 2.4 端末で使えない部品の見張り

**【踏襲】** 拡張機能の `test/unit/cross/browserReach.test.ts` と同じ形で、Android の入口から `import` を静的にたどり、`vscode`・`node:` で始まるもの・`undici` を取り込んでいないかを見張るテスト（`androidReach.test.ts`）を置く。2026-11-05 に置いた（`test/androidReach.test.ts`）。入口は `src/main.ts` で、本体の部品（`node_modules/novel-ai-assistant/src/...`）の中までたどる。CI の Windows のジョブで毎回走る。静的な `import` は呼ばれなくても読み込まれ、端末では起動した瞬間に落ちるためである（拡張機能の CLAUDE.md の失敗6）。

| # | 問い | 答え | 印 |

| 1 | 手元の AI をどう扱うか | クラウドの AI と、作者のパソコンの Ollama・LM Studio の両方を選べるようにする。スマホの中では AI を動かさない。パソコンの Ollama を呼ぶときも、共通設計書 2.6 の4つ（`num_ctx` の明示・`format` にスキーマ・`think: false`・モデル情報は API から）を同じコードで守る。**パソコンへは Tailscale（端末どうしを暗号化した専用の道でつなぐ道具）の道だけで送る。** 家の Wi-Fi の上で直に `http://` で送る形は作らない。理由は3つ：①家の Wi-Fi の中では本文が暗号化されず、同じ Wi-Fi の機器から覗ける ②Ollama には合言葉が無く、直に届くようにすると同じ Wi-Fi の機器が誰でも使え、モデルも消せる ③カフェの Wi-Fi も 192.168.x.x なので、番地だけでは家かどうか分からず、外で知らない人のパソコンへ本文を送りうる。**宛先は作者が登録したパソコンだけ**とし、番地だけで信用しない。宛先が既定と違うときは宛先を見せる（設計書 6.78）。Tailscale の道なら外出先からも家の Ollama を使える | 【決定】2026-10-31 作者「Tailscale 経由だけ」（「セキュリティは守れますか？」への説明を受けて） |

## 4. 画面の作り（幅で3段）

**【決定】** 2026-10-29 作者「幅で3段」。画面の幅で、1枚・2枚・3枚の並べ方を切り替える。

### 4.1 段の境目

| 段 | 窓の幅 | 端末の例 | 並べるもの |
|---|---|---|---|
| 狭い | 600dp 未満 | スマホの縦 | 1枚ずつ。下のタブで切り替える |
| 中 | 600dp 以上 840dp 未満 | スマホの横・小さいタブレット・折りたたみを開いた状態 | 2枚：話の一覧と原稿 |
| 広い | 840dp 以上 | 大きいタブレット・タブレットの横 | 3枚：話の一覧と原稿と横の板（提案・資料・メモ） |

境目の 600dp と 840dp は、Android が窓の大きさを分ける区分（compact・medium・expanded）と同じ値にする。ほかのアプリと同じ所で並べ方が変わるので、回転や分割画面で作者が戸惑わない。

**段は窓の幅だけで決める。** 端末の種類（スマホかタブレットか）では決めない。同じタブレットでも、分割画面で半分にすれば中や狭いになる。

**画面の部品は1つずつ作り、段では並べ方だけを変える。** 同じ原稿エディターを段の数だけ作らない。作ると、直したときに片方だけ直る。

### 4.2 画面の一覧

| 記号 | 画面 | 中身 |
|---|---|---|
| A | 作品一覧 | 作品ごとに、題・話数・字数・最後に書いた日・同期の状態（送っていない話の数・競合の印） |
| B | 話の一覧 | 章ごとに話を並べる。各話の字数と印（送っていない・校閲中の鍵・競合・話数の重複や欠番）。いちばん新しい話を書く入口を先頭に置く |
| C | 原稿エディター | 5章 |
| D | 提案 | 誤字脱字・推敲・矛盾・逸脱・編集部の提案・設定資料の更新を1か所に集める（共通設計書 5.6）。1件ずつ［採る］［見送る］。まとめて採る操作は、拡張機能と同じ決まりで置く |
| E | 設定資料 | 人物・場所・組織・能力・世界観・伏線の一覧と1件の表示。作者の書いた欄（`authorNotes` など）にはそれと分かる印を付ける |
| F | AI を走らせる | 機能を選ぶ → 範囲を選ぶ → **処理量と費用の見積もり** → 走らせる → 進み具合と［中止］（7章） |
| G | 同期 | GitHub と同期・状態・競合のときの選び方（6章） |
| H | 設定 | AI・GitHub・表示（書体・文字の大きさ・縦横の既定） |
| I | 執筆統計 | 今日・今週の字数。端末ごとに記録して、表示のときに足す（共通設計書 3.4） |

### 4.3 段ごとの並べ方

**狭い（スマホの縦）**

- 下のタブは4つ：**作品**（A→B）・**書く**（C）・**提案**（D）・**ほか**（E〜I）
- ［書く］は最後に開いた話を開く。作品を開いたあとは、ほぼこのタブにいることになるため、押す回数を減らす
- ［提案］には未決の件数を付ける
- 原稿エディターを開いているあいだ、下のタブは隠してよい（キーボードが出ると狭いため）。上のバーの［戻る］で戻る

**中（スマホの横・小さいタブレット）**

- 左に話の一覧（幅 280dp）、右に原稿エディター
- 提案・資料は右から出す引き出しにする。原稿を隠さず、半分の幅で重ねる
- 左の一覧は畳める。畳むと原稿が全幅になる

**広い（大きいタブレット）**

- 左に話の一覧（260dp）、中に原稿エディター、右に横の板（320dp）
- 横の板は［提案］［資料］［メモ］のタブで切り替える。原稿で選んだ語の資料・指摘の場所へ、横の板から飛べる
- 左と右は別々に畳める

### 4.4 入口（右クリックの代わり）

拡張機能の入口は右クリックとコマンドである。Android には両方とも無い。

- **長押しの品書き**：原稿で字を選ぶと、選んだ範囲の近くに帯を出す。中身は［ルビ］［傍点］［資料を見る］［AI に訊く］と、Android の［コピー］［貼り付け］。Android の文字選択の帯に項目を足せるか（ネイティブの側の作業）は【確かめる】。足せなければ、選んだ範囲の下に自前の帯を出す
- **上のバーの［…］**：作品と話の操作（新しい話・章を立てる・書き出し・AI を走らせる）
- **キーボードの付いたタブレット**：拡張機能と同じショートカット（設計書 6.25.10。Ctrl+S・Ctrl+Z など）を効かせる

#### 4.4.1 機能の多さをどう並べるか（3段）【案】

拡張機能の詳細メニューは百を超える操作を「分類 → 小分類 → 操作」の木で並べている。**この木はそのまま持ってこない。** 狭い画面で深い木をたどるのは手数が多く、作者がいちばん長くいる［書く］を押しのけるためである。入口を次の3段に分ける（作者の問い 2026-10-31「膨大なメニューを、Android ではどのように整理するのが良いでしょうか？」への設計の側の案。試作で触ってから決める）。

1. **いつも見えるもの**：下のタブ（4.3）と上のバーだけ。数を増やさない
2. **その場で出すもの**：触っている所で絞った操作だけを、長押しか選んだときに出す。**一度に5〜7個まで**で、階層は作らない
   - 話の一覧で話を長押し → その話の誤字脱字・推敲・あらすじ
   - 原稿で字を選ぶ → 4.4 の帯（ルビ・傍点・資料を見る・AI に訊く）
   - 設定資料の1件 → 本文から読み直す・関係を見る
   - 提案（D）→ 採る・見送る・まとめて
3. **探して呼ぶもの**：［ほか］の中の「すべての機能」。木ではなく**検索欄つきの一覧**にする（コマンドパレットと同じ考え方。打ちにくい画面では2〜3文字で絞れることが効く）。あわせて、
   - **「AIに相談」を入口として使う。** はっきり頼めばその場で動く（拡張機能 0.116.1、共通設計書 5.7）ので、場所を覚えなくても「表記ゆれを見て」で済む
   - 簡単ステップメニュー（次にやることの案内）はそのまま持ってくる

- **端末で使えない操作は、どの段にも出さない**（共通設計書2章の冒頭。PDF の印刷・git の細かい操作・Ollama の設定など）
- **2段目に載せる操作は、使われている数から選ぶ。** 拡張機能の動作の記録で、作者がどの操作を何回使っているかを数えてから決める（感覚で選ばない）
- 3段目の一覧の名前は、拡張機能の詳細メニューの題と同じ字にする（相談の AI が名前で案内するため。設計書 6.104）

#### 4.4.3 作品を足す・外す【案】

作品はアプリ専用の置き場に置き、GitHub 同期でパソコンと行き来する（3章 #2【決定】）。そのため「作品を足す」は、拡張機能の「フォルダーを選んで登録」とは別物になる（作者の問い 2026-10-31「作品登録や AI の切り替え等、詳細メニューのような内容はどうなっているでしょうか？」への案）。

- 作品一覧（A）の右下に［＋］を置き、押すと2つから選ぶ
  - **GitHub から取り寄せる**：作者のリポジトリを一覧から選ぶ。パソコンで書いている作品を持ってくる、いちばん多い使い方。取り寄せは浅い取得（6章）
  - **新しく作る**：題を入れるだけで作る。GitHub に置き場を作るかは、作ったあとに訊く

### 4.5 回転・分割画面・キーボード

- 回転や分割画面で段が変わっても、開いている話・カーソルの位置・書きかけは保つ
- キーボードが出たら原稿の見える高さを縮め、カーソルを見える所へ動かす。段は変えない（キーボードは窓の幅を変えないため）
- 段が変わる瞬間に変換中の字があれば、変換が確定するまで並べ替えを待つ。並べ替えで入力欄が組み直されると、変換中の字を失うためである（設計書 6.25.1 と同じ考え方）

## 5. 原稿エディター

作者がいちばん長く触る画面である。**壊れたときの被害が原稿そのもの**なので、拡張機能で積んだ守り（設計書 6.25・6.34）を、そのまま持っていく。

### 5.1 面と向き

面は拡張機能と同じ2つ。どちらにも縦と横がある。

| 面 | 作り | 役目 |
|---|---|---|
| **組んで書く**（既定） | `contenteditable` | ルビ・傍点を組んだまま打てる |
| **書く** | `<textarea>` | 記法をそのまま見せる（`{漢字|かんじ}`）。日本語入力を細工せずに効かせる土台 |

**【案】** 拡張機能の原稿エディターの画面（`views/manuscriptEditorHtml.ts`）は、VS Code との受け渡し（送る・受け取る）を除けば、端末に依らない HTML である。受け渡しの口だけを差し替えて、画面の中身は共有する。別に作り直すと、拡張機能で直した日本語入力の不具合（設計書 6.25.1〜6.25.11）を、もう一度踏むためである。共有できる形に分けられるかは最初の試作で確かめる。

### 5.2 縦書きで打つ

**【決定】** 2026-10-29 作者「縦でも書ける」：スマホでも縦書きのまま打てるようにする。

- 組み方は拡張機能と同じ：`writing-mode: vertical-rl`・`text-orientation: mixed`・半角1〜2字の縦中横・行末の約物を詰めない（`text-spacing-trim: space-all`。設計書 6.34.5）。組む規則は `core/manuscriptRender.ts` を共有する
- 行は右から左へ進み、画面は横へ送る。打っているあいだは、カーソルのある行が見える位置へ自動で送る
- 文字の大きさは2本指で広げる・つまむ操作で変える。変えた大きさは端末ごとに覚える
- **書体【決定】** 2026-10-31 作者「後から入れられるように」：最初は端末の書体で組む（明朝が無い端末ではゴシックになる）。**設定から明朝（Noto Serif JP。SIL Open Font License）を取り寄せて使えるようにする。** アプリには同梱しない（同梱すると十数MB重くなるため）。取り寄せる書体は、原稿にはどの字も出うるので、字を間引いた軽い版にはしない。取り寄せたあとはアプリ専用の領域に置き、通信の無いときも使える。取り寄せる前にファイルの大きさを示す

**Android の日本語入力で縦書きの入力欄が崩れないかは、まだ誰も確かめていない。** 拡張機能でも縦書き×`contenteditable`×日本語入力は実機でしか確定しなかった（設計書 6.34.1）。最初の試作で、次を作者の実機で確かめる。

| 確かめること | 日本語入力 |
|---|---|
| 変換中の字が消えない・二重にならない | Gboard を先に。作者が使う日本語入力があればそれも |
| 変換の候補を選んで確定したとき、カーソルが飛ばない | 同上 |
| 改行・1字消す・範囲を選んで消す | 同上 |
| 長押しで選んだ範囲が、縦の行に沿って伸び縮みする | — |
| キーボードの上下で、カーソルの行が隠れない | — |
| 組んで書く面で、ルビの直前・直後に打てる | 同上 |

### 5.3 崩れたときの道

縦書きで打てない端末と日本語入力の組み合わせがあっても、作者が書き続けられるようにする。

1. **上のバーに［横で書く］を常に置く。** 押すと、同じ話の同じ位置のまま横書きの面へ移る。戻すのも同じボタン
2. **打った字が本文へ届いたかを、便ごとに確かめる**（設計書 6.25.9 と同じ仕組み）。食い違いを見つけたら、その場で「この端末では縦書きの入力が崩れることがあります。横で書くと確実です」と出し、［横で書く］へ案内する。**自動では移さない。** 打っている最中に面が変わると、変換中の字を失うためである
3. **組んで書く面は、入る前に「記法 → 表示 → 記法」の往復が本文と完全に一致するかを確かめ、一致しなければ開かない**（設計書 6.34.5 と同じ）。書く面（textarea）へ回す
4. **書きかけは打鍵ごとに端末に控える**（`.aiwriter` の外、同期しない場所）。面を移っても、アプリが止められても、字を失わない。控えは保存が済んだら消す

崩れた組み合わせは端末の型と日本語入力の名前で端末に覚え、次からは開いたときに一度だけ知らせる（勝手に横へは開かない）。

### 5.4 保存

拡張機能は保存を VS Code に任せていた。Android では自分で持つ。

- **自動で保存する。** 打つのを止めて2秒たったとき、話を移るとき、アプリが裏に回るとき【決定】2026-10-31 作者「案どおり」（次の行の退避の取り方も）
- 保存は必ず `writeTextFilePreservingFormat` を通す（共通設計書 2.1）。保存のたびに退避が積まれると5世代がすぐに埋まるので、**退避は話を開いて最初の保存のときだけ**にする【決定】。2秒ごとの退避で、開く前の本文が5回で押し出されるためである
- 保存の直前のハッシュが読んだときと違えば（同期で本文が入れ替わったなど）書かずに止め、書きかけを控えに残したまま「外で変わりました」と知らせる。作者が［あちらを見る］［こちらで上書きしない］から選ぶ。上書きの道は置かない
- 上のバーに保存の状態を小さく出す（「保存済み」「保存待ち」）

### 5.5 取り消し

拡張機能は取り消しを VS Code の文書に任せ、画面は自前の取り消し履歴を持たない（設計書 6.34.4）。Android には任せる先が無い。

**【案】** アプリが本文の中身を持ち、打鍵ごとに「変わった1か所」を手として積む。取り消しはその手を1つずつ戻す。ブラウザの取り消し（`contenteditable` の取り消し）は使わない。組み直すたびにブラウザの履歴は壊れるためである。ルビ・傍点を振る操作も1手として積む。

### 5.6 キーボードの上の道具帯

スマホのキーボードで打ちにくいものを、キーボードのすぐ上の1列に置く【案】。**並びは試作で作者が実機で打ってから決める**（2026-10-31 作者「試作で打ってから決める」）。試作は次の並びで作る。

［取り消し］［やり直し］［ルビ］［傍点］［「」］［――］［……］［横で書く／縦で書く］

- 「――」と「……」は2字を1押しで入れる
- ［ルビ］は選んだ範囲に振る。選んでいなければ、カーソルの前の漢字のまとまりに振る
- 道具帯は横へ送れる。並びは作者が変えられる（後の段）

### 5.7 用語の色・ルビ・傍点

- 用語の色は CSS Custom Highlight API（設計書 6.34.3 と同じ）。使えない WebView では色を出さない。本文の組み立てには影響しない
- ルビ・傍点は「編集できないかたまり」として置く（設計書 6.34.2）。消すときは1つで消える
- 語を長押しして［資料を見る］を押すと、狭い段では資料を下から半分の高さで出し、中・広い段では横の板に出す

## 6. 同期

決まりは共通設計書 2.8。ここでは Android の動きだけを書く。

- **取ってくるのは自動**：アプリを開いたとき・前に出たとき。早送りできるときだけ取り込む
- **送るのは作者が押したとき**：作品一覧と話の一覧に「送っていない話」の数を出し、押し忘れに気づけるようにする
- **競合したら、両方とも残す**：話ごとに［こちら］［あちら］［両方残す］を選ぶ画面を出す。選ぶまで、その話には AI を当てない
- **通信が無くても書ける**。同期は通信が戻ってから
- **初めて取ってくるときは、新しい1つ分の歴史だけを取る**（浅い取得）。スマホの容量と通信量を節約するためである。古い歴史は要るときに取る
- `isomorphic-git` で「競合の印を書く合流」ができるかは【確かめる】。できなければ、競合した話は両方の中身をファイルに分けて残し、作者に選んでもらう

## 7. AI

- 機能ごとの AI の割り当て・落とし先・有料の AI の前の確認は、共通設計書 4.2〜4.4 のとおり
- **AI の切り替えは2か所に分ける【案】**（作者の問い 2026-10-31 への案。4.4.3 と同じ問い）
  - **設定（H）→ AI**：使う AI の登録（クラウドの AI と、パソコンの Ollama・LM Studio）・鍵・機能ごとの割り当て。拡張機能の「AI の割り当て」にあたる。たまにしか触らない所
  - **走らせる直前の見積もり（F）**：「どの AI で」の行を押すと、**その回だけ**別の AI に替えられる。設定は書き換えない。料金のかかる AI に替えたら、見積もりの費用の目安が出直す（共通設計書 4.4）

## 12. iOS へ広げるとき

**【決定】** 2026-10-31 作者「それでいきましょう」：iOS 版も Android と同じ分け方で作る。中身（共有コード）と画面は TypeScript、ネイティブが要る所だけをその端末の言語で書く。ネイティブの言語は Android では Kotlin、iOS では Swift。包む土台は同じ Capacitor。

**【決定】** 2026-11-02 作者「同じリポジトリで、iOS版まで開発します」：iOS 版は別のリポジトリに分けず、このリポジトリで作る。リポジトリの名前も同じ日に `novel-ai-android` から `novel-ai-mobile` へ改めた。Capacitor は1つのプロジェクトに `android/` と `ios/` を並べて置けるので、画面と共有コードを1つのまま、Android と iOS の両方を組み立てる。

**【未決】** iOS 版を組み立てる場所。Xcode は Mac でしか動かないので、手元か借りた Mac で組むか、GitHub Actions の macOS の機械で組むかのどちらかになる。作者はまだ決めていない（11章 #4）。

Android のために書いたものは、ほぼそのまま持っていける。書き直すのはネイティブの部分（Swift）と、次の表で「違う」とした所だけにする。Android の側で書くときも、iOS で困る形（Android にしか無い仕組みを `core` や画面の側で直に呼ぶ形）にしない。端末の事情は 2.3 の差し替える部品の中に閉じ込める。

| 所 | Android | iOS | 扱い |
|---|---|---|---|
| 画面の描き手 | WebView（Chromium） | WKWebView（WebKit。Safari と同じ） | 縦書き・ルビ・日本語入力と `contenteditable` の組み合わせは、iOS の実機で別に確かめる（5.2 の表を iOS でもなぞる）。行末の約物を詰めない指定（`text-spacing-trim`）が WebKit でどこまで効くかは【確かめる】 |
| 長い AI の処理 | 裏でも続ける（前面のサービス。7章） | 裏に回すと短い時間で止められる | iOS では裏で続けない。止められたら、チャンクの控え（共通設計書 2.4）で次に開いたとき続きから走らせる |
| 書体 | 端末の書体で始め、明朝は取り寄せる（5.2） | ヒラギノ明朝が入っている | 取り寄せは要らない。端末の書体のまま明朝で組む |
| 手元の AI | Tailscale の道だけ（3章 #1） | 同じ（iOS 版の Tailscale がある） | 同じ作り。iOS は家の中の通信に端末の許可（ローカルネットワーク）が要るが、Tailscale の道なら要るかは【確かめる】 |
| 鍵の保管 | Android Keystore | キーチェーン | 2.3 の鍵の保管の差し替えを足す |
| 作品の置き場 | アプリ専用の領域（3章 #2） | アプリ専用の領域（Documents） | 同じ作り。GitHub 同期で行き来する |

| 配布 | Google Play | App Store。Apple Developer Program（年 99ドル）の登録が要る | 実機での試しは TestFlight で配る |
